# 桌面插件排障手册：把「猜」换成「取数」

这份文档不是这次 bug 的复盘记录，而是**下次遇到同类问题可以直接照做的方法**。
来源是一次真实排障：DSH 桌面插件里，`Alt+Q` 松手切换在官方 DSH NEXT 上反复「卡住」，在社区版 dsh-desktop 上却一直正常。前后错了三次假设，最后靠探针一次性定位。

方法的核心只有一句：**在真实运行时取数，用最小实验区分互斥假设；不要用读代码代替观测。**

---

## 一、先分类：差异有四种来源

碰到「A 能跑、B 不能跑」，先别急着读代码，先判断差异属于哪一类。分类错了，后面全是白费。

| 类别 | 判断方式 | 本次实例 |
| --- | --- | --- |
| 代码不同 | 两个版本的同一文件逐字比对 | `lib/main.js` 的输入处理**逐字相同**，排除 |
| 配置不同 | 比对运行时报告的 profile / mode / runtime | NEXT 报 `runtime: "desktop"`，社区版报 `"web"` |
| 运行时不同 | 同一个 API 在不同宿主里行为不同 | `setIgnoreMenuShortcuts` 只在录制态可达 |
| 时序不同 | 事件什么时候到、谁先谁后 | 命令派发早于页面拿到按键 |

**本次教训**：我一开始默认「代码不同」，花了两轮比对 `main.js` 才排除。其实第一步就该问「两边运行时报告了什么」，那个值一行日志就能拿到。

---

## 二、探针设计：每个探针必须能排除一个假设

烂探针：「进到这里了」。
好探针：**能区分互斥可能**。

本次最终用的是三处日志，每一处都对应一个「如果……就说明……」：

```
[kana-probe] enter mode=... switcher=true page=true focus=true board=null
[kana-probe] base-down KeyQ altKey=true pre=true
[kana-probe] open ... baseDown=none baseUp=none altUp=none tap=false
```

- `enter` 有、`base-down` 没有 → **命令到了，但页面没收到按键**
- `enter` 都没有 → **命令压根没派发**（主进程层）
- `baseDown/altUp` 有但 `tap=false` → **时间窗判断错了**，不是信号缺失

三条日志就能把「没派发 / 没收到 / 判断错」三种病因分开，不用来回试。

**写探针的三条纪律**：

1. **带统一前缀**（如 `[kana-probe]`），方便在控制台筛，也方便最后一次性删干净。
2. **打完就删**。残留的 `console.log` 会在正式版里变成噪音，也要用一条命令确认删干净：
   ```powershell
   Select-String -Path client.js -Pattern 'kana-probe' | Measure-Object
   ```
3. **删完立刻跑测试与语法检查**。本次按行过滤把跨行日志切断了，留了个孤儿行导致语法错误，是 `node --check` 抓到的。

---

## 三、绕开自己代码：手装最原始的监听器

这是本次最有效的一步，成本几乎为零。

在控制台粘贴：

```js
window.addEventListener('keydown', e => console.log('RAW down', e.code), true);
window.addEventListener('keyup', e => console.log('RAW up', e.code), true);
```

**它的价值在于把「事件有没有到页面」和「我的代码有没有处理」彻底分开**：

- 有 `RAW`、没自己的日志 → 是自己的监听器没注册 / 被移除 / 注册太晚
- 两边都没有 → 事件根本没进这个渲染进程，往宿主层查

本次正是靠它看清：页面只收到 `RAW down AltLeft`，之后 `Q` 和 `Alt` 的松开**一条都没有**。这是读多少代码都推断不出来的事实。

---

## 四、排除观测污染，再下结论

三条必查：

1. **控制台「保留日志」（Preserve log）是否开着**——开着会把上一次会话的日志混进来。本次就被带偏过一次：以为板子在按键前就打开了，其实是旧日志。
2. **焦点在哪**——按住 DevTools 窗口时按键不进页面，测试结果无效。
3. **状态是否残留**——宿主可能缓存按键状态。本次主进程的 `held` 集合里残留了上一次没收到 keyup 的 `KeyQ`，导致「没按 Q 却触发组合」。**每次重测前重启客户端**，比解释异常便宜。

## 五、状态机类 bug：找「谁该复位」

凡是「第一次正常、第二次坏」的现象，几乎都是某个标志位没有复位。

本次：`preArm.on` 在提交后仍是 `true`，导致第二次按 `Alt` 时提前返回、不再接管键盘 → 卡住。而 `Esc` 走的是另一条关闭路径，把状态彻底清了，所以第三次又正常。

**排查套路**：

1. 复现「第一次好、第二次坏」；
2. 找那个「用一次就该失效」的标志；
3. 在每个退出路径（提交 / 取消 / 失焦 / 超时）上都复位它；
4. 补一条**连做两次**的测试，否则这类 bug 永远逃过单元测试。

本次新增的两条测试就是干这个的：一条覆盖「主进程吞掉基础键」的盲区，一条覆盖「连续两次」的复位。

---

## 六、新增「全局接管」时必须一起定义三件事

凡是让插件临时接管键盘 / 焦点 / 剪贴板，都要同时回答：

1. **什么时候开始**（触发条件要尽量窄——本次收窄为「裸按 Alt」，带 Ctrl 的组合不接管，于是 `Ctrl+Alt+D` 没被误伤）
2. **什么时候归还**（正常结束 / 无关按键 / 超时 / 失焦，四条路径都要有）
3. **接管期间谁被连累**（本次：按住 Alt 期间其它 Alt 组合会静音，必须写进 README，而不是等用户来报）

**第三条最容易被漏掉**。功能做通了不等于没代价，代价要主动写出来。

---

## 七、改之前先能证明「改哪一行」

本次三次错误假设的代价：

| 假设 | 结论 | 代价 |
| --- | --- | --- |
| 菜单吞了 Alt 松开 | 部分正确，但不是全部 | 改了 `recording` 捕获 |
| 主进程 `preventDefault` 让页面收不到基础键 | 错，页面能收到 | 改了轻点判定 |
| 运行时 `runtime` 不同导致规则不同 | 正确但只是表层 | 解锁社区版 |

真正的根因（按住 Alt 后整段键盘被窗口接管）是在**手装 RAW 监听器**之后才浮现的。

**所以流程应该是**：

```
现象 → 分类（代码/配置/运行时/时序）
     → 一个能区分互斥假设的探针
     → 真实运行时取数
     → 只有数据支持时才动代码
     → 改完立刻跑测试，并补一条守住这次结论的用例
```

**最后一条最值钱**：每定位一个 bug，就补一条测试把它钉住。否则下次重构会悄悄改回去——本次那两条新测试，就是防止有人再把「主进程盲区」和「复位」丢掉。

## 八、可以直接抄的清单

排查桌面（Electron）插件问题时按顺序过：

- [ ] 两套客户端报的 `runtime` / `platform` / `mode` 分别是什么？
- [ ] 同一段宿主代码是否逐字相同（用 asar 解包比对，别凭印象）？
- [ ] 手装 `RAW` 监听器：按键到底有没有进页面？
- [ ] 控制台关了 Preserve log 吗？清空了吗？焦点在页面上吗？
- [ ] 宿主有没有残留按键状态（重启再测一次）？
- [ ] 现象是「第一次好第二次坏」吗 → 找该复位的标志位
- [ ] 有没有临时接管键盘 / 焦点 → 开始、归还、连累面都定义了吗？
- [ ] 改完：语法检查 + 全量测试 + **补一条钉住结论的用例**
- [ ] 探针删干净了吗（grep 一遍）？文档写了代价吗？

## 附：本次真正的事实（供以后参考）

- Windows 上**单独按下 `Alt`** 会被窗口菜单接管，之后该窗口的页面收不到任何按键，包括 `Alt` 自身的松开。
- Electron `before-input-event` 里 `event.preventDefault()` 只影响默认行为，**页面仍可能收到 DOM 事件**——不要假设「preventDefault 等于页面收不到」。
- `setIgnoreMenuShortcuts(true)` 是唯一能让 `Alt` 留在页面的开关，而 DSH 只在 `shortcuts.recording(true)` 时打开它；代价是**同时静音全部原生快捷键派发**。
- 宿主的 `held` 集合依赖 keyup 清理；一次被吞掉的 keyup 会让残留键参与后续组合判断，产生「没按却触发」。
- DSH 对 Web 运行时（`runtime === "web"`）有硬规则：只放行含 `Ctrl` 的双修饰键组合，纯 `Alt` 一律拒绝。社区版就是 web 运行时。
